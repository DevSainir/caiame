# Caiame

Образовательная платформа: академия одного вендора. Мы публикуем курсы, студенты покупают
доступ и проходят их — видеоуроки, тесты с автопроверкой, задания с ручной проверкой.
FastAPI + Vue 3 SPA, PostgreSQL, всё в Docker. Один сервис, одна база, один деплой.

Бэкенд — слоистая (clean) архитектура: верхний уровень `backend/src/` — это слой
(`routers`, `services`, `repos`, `models`, `schemas`, `core`, `integrations`), внутри слоя —
файл на сущность. Провайдеры зависимостей в `core/deps.py`, агрегатор роутеров —
`routers/router.py`. Фронтенд разложен по областям: `frontend/src/features/<name>/`.

## Инварианты репозитория

Пять правил, которые дешевле прочитать здесь, чем узнать из упавшего теста:

* **Слои идут в одну сторону**: `routers` → `services` → `repos` → `models`. Роутер не
  видит ORM-модель, SQL не пишется выше репозитория, бизнес-правило живёт в сервисе.
* **Решение, которое уже принимает чужой сервис, зовут, а не повторяют.** Это единственное
  правило про связи между сущностями; фасадов, `contract.py` и запретов на импорт соседа
  здесь нет.
* **Границу транзакции держит зависимость сессии.** Сервисы и репозитории не коммитят:
  один запрос — одна транзакция.
* **Каждый путь ввода-вывода асинхронный** — сессии БД, HTTP-клиенты, работа с хранилищем.
* **500 строк — жёсткий потолок файла** (250 для `.vue`), 300 — момент задуматься о
  разбиении. Делим по ответственности, никогда `part1`/`part2`.
* **В коде только английский** — имена, докстринги, комментарии, `detail` ошибок, описания
  в `responses={...}`, имена тестов. Русский живёт в интерфейсе, в документации и в
  разговоре с человеком.

Направление слоёв и потолок строк стоит закрепить одним тестом в `backend/tests/unit/core/`
в первый же день, правила импортов фронтенда — в `frontend/eslint.config.js`. Постфактум
такая проверка находит два десятка нарушений, и её хочется отключить.

**Ворота качества обязательны и не пропускаются**: ruff (lint + format), `mypy --strict`,
pytest со строгими маркерами, pre-commit, поднимающий всё это на каждом коммите. `# noqa` и
`# type: ignore` — только с кодом правила и причиной; ослабление конфига — отдельное
решение, а не побочный эффект задачи. Настройки и обоснование каждой — в
`backend-architecture`.

**Предметные области (курсы, обучение, проверка знаний, оплата, медиа) — карта продукта, а
не дерево каталогов.** Список открыт, границы двигаются, перенос файла — обычная правка.
Подробнее — в `backend-architecture`.

## Где остальные правила

Правила проекта лежат скиллами в `.claude/skills/` — `backend-architecture`,
`frontend-architecture`, `design-system`, `learning-domain`, `assessments`, `media-video`,
`payments-access`, `security`, `testing`, `git-workflow`. Описание каждого говорит, когда он применяется,
поэтому они подключаются сами, а не занимают место в каждом разговоре. Это обычный
markdown — читай напрямую, если работаешь без этого механизма, и клади новые правила
проекта в подходящий скилл, а не сюда.

Три вещи, которые стоит знать до того, как открыть скилл:

* **Прогресс — производная, а не поле.** Проценты считаются из фактов по урокам; хранимая
  цифра расходится с реальностью молча. `learning-domain`.
* **Доступ решает один метод** `services/billing.py::has_access`, и он отвечает «нет» на
  любую неизвестность. Никто, кроме него, не ходит в таблицы заказов. `payments-access`.
* **Правильные ответы теста не покидают бэкенд** — не фильтрацией полей, а отдельной
  схемой, в которой поля нет. `assessments`.

## Команды

```bash
make test-fast        # юнит и компонентные бэкенда, юнит фронтенда — гейт перед коммитом
make test-integration # настоящий Postgres (пропускается, если недоступен)
make lint typecheck   # ruff + eslint + mypy --strict
```

`make` без цели перечисляет все запускалки.
