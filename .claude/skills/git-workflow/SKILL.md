# Git-процесс

## Транковая разработка: коммит в `main`

**Ветки под задачи не заводим.** Работа попадает в `main` маленькими коммитами и пушится
по мере готовности. PR для обычной работы не открывается, ничего не ждёт ревью, чтобы
влиться.

Это значит, что привычный рефлекс «я на основной ветке — сначала создам свою» здесь
**неверен**: `main` и есть рабочая ветка.

Что транковая разработка требует взамен и что реально имеет значение каждый день:

* **Маленькие коммиты, частые пуши.** Работу ветки — держать незаконченное в стороне от
  всех — теперь выполняет размер коммита. Если изменение нельзя закоммитить, не сломав
  `main`, оно слишком большое; раздели его так, чтобы каждый коммит стоял сам по себе.
* **`main` остаётся зелёным.** Хуки перед коммитом (ruff, `mypy --strict`, eslint,
  prettier, проверка сообщения) — это ворота, и они срабатывают на каждом коммите. Не пуш
  поверх падающего: спрятать поломку негде.
* **Незаконченная функциональность прячется за флагом, а не за веткой.**

Единственное исключение — изменение, которое действительно нельзя разделить и которое
оставит `main` сломанным посередине. Это редко настолько, что стоит сказать вслух тому,
кто попросил, а не молча завести ветку.

## Какой тип

Номер версии **выводится из типов коммитов**, а не пишется руками, поэтому выбор типа — это
решение о релизе, а не ярлык.

| Тип | Версия | Когда |
| --- | --- | --- |
| `fix:` | patch | дефект в поведении, которое уже выкатили |
| `feat:` | minor | новая возможность для пользователя: страница, отчёт, тип урока, интеграция |
| `perf:` `refactor:` `docs:` `test:` `chore:` `ci:` `build:` `style:` | patch | без изменения пользовательского поведения |

Ломающее изменение (`!` или футер `BREAKING CHANGE:`) до версии 1.0 остаётся **minor** —
это осознанно, чтобы один восклицательный знак не объявил проект стабильным раньше, чем
кто-нибудь это решил.

Если поток мелких возможностей начнёт делать минорную версию бессмысленной, заводится
собственный тип вроде `feat-minor:` (patch-бамп для мелочи, которую никто не станет
объявлять). Он не входит в спецификацию Conventional Commits, поэтому его придётся
зарегистрировать в конфигурации хука, линтера сообщений и релизного инструмента — три
места, и все три надо будет найти. Пока потока нет — не заводи.

## Область (scope)

Область — это предметная область продукта: `auth`, `catalog`, `learning`, `assessments`,
`billing`, `media`, `core`, `frontend`. В дереве каталогов бэкенда её нет (см.
`backend-architecture`), она живёт только в разговоре и вот здесь — зато по истории видно,
что и где менялось, без чтения диффов. Список не закрыт: появилась область — пиши её.

## Сообщение

Заголовок в повелительном наклонении, по-русски или по-английски — но одинаково во всём
репозитории, выбери один раз. Тело — про **почему**, и его стоит писать: эти сообщения
становятся списком изменений, который потом читают люди. Пересказывать то, что и так видно
в диффе, не нужно.

```
feat(assessments): добавить ограничение времени на попытку

Таймер считается от started_at на сервере: клиентские часы подводились,
и попытка оставалась открытой сколько угодно.
```

Заканчивай каждый коммит строкой соавторства, если он написан вместе с ассистентом:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

## Чего не делаем

* Не коммитим секреты — `.env` в `.gitignore` с первого коммита, а не после первой утечки.
  Попавший в историю ключ считается скомпрометированным, даже если следующий коммит его
  убрал; такой ключ отзывают, а не «удаляют из репозитория».
* Не коммитим сгенерированное: `dist/`, `__pycache__/`, снимки покрытия, загруженные файлы.
* Не переписываем историю в `main` (`push --force`). Локальную неопубликованную — сколько
  угодно.
